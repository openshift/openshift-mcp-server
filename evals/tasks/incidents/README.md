# Incidents evaluation tasks

These tasks exercise the `get_incidents` tool of the `observability/incidents`
toolset (OpenShift cluster health analyzer incidents) against live
Prometheus/Alertmanager backends.

Unlike the other suites, these tasks require an **OpenShift cluster**: the
toolset only exposes `get_incidents` when the `monitoring` UIPlugin has
`spec.monitoring.clusterHealthAnalyzer.enabled: true`, and incident-to-
component mapping relies on the in-cluster cluster-health-analyzer.

## Prerequisites

- OpenShift cluster access (`oc login`) with the monitoring UIPlugin
  cluster health analyzer enabled
- The `observability/incidents` (or `observability/metrics`) toolset
  configured with **HTTPS** `prometheus_url` (Thanos Querier) and
  `alertmanager_url` (Alertmanager) endpoints — both backends must use
  HTTPS — and `auth_mode = "kubeconfig"`
- Synthetic always-firing alerts so the tasks have deterministic incidents
  to query (see below)
- MCP server started with `observability/incidents` in `TOOLSETS`

## Synthetic alerts

`shared/alerts-prometheusrule.yaml` defines three always-firing alerts
(`etcdHighFsyncDurations` and `KubePodCrashLooping` at warning severity,
`etcdMembersDown` at critical severity) that map to known components, so
`get_incidents` returns deterministic data. Apply it before running the
evals and remove it afterwards:

```bash
oc apply -f shared/alerts-prometheusrule.yaml
# wait until the alerts fire and the cluster health analyzer maps them:
#   count(ALERTS{test_type="mcpchecker-eval",alertstate="firing"}) >= 3
#   count(cluster_health_components_map{src_alertname=~"etcdHighFsyncDurations|KubePodCrashLooping|etcdMembersDown"}) >= 3
# cleanup:
oc delete prometheusrule -n openshift-monitoring -l test-type=mcpchecker-eval
```

Each task's judge criteria expect these alert names in the agent's answer.

## Task overview

| Task                   | Difficulty | Description                                             |
|------------------------|------------|---------------------------------------------------------|
| backend-reachability   | easy       | Smoke test: tool reachable, valid response              |
| list-incidents         | easy       | List firing incidents and summarize                     |
| critical-incidents     | medium     | Use the `min_severity` filter for critical only         |
| recent-incidents       | medium     | Use the `time_range` filter for the last 24 hours       |
| cluster-health-summary | hard       | Multi-step reasoning: overall health assessment         |

## Running locally

Everything lives under `_output/` (gitignored — the embedded token cannot be
committed). The commands below create the two input files; the rest is
generated by the `make` targets.

### 1. Backend config — `_output/incidents-config.d/`

The URLs are the OpenShift platform-monitoring routes, looked up from the
cluster:

```bash
mkdir -p _output/incidents-config.d
cp dev/config/mcp-configs/000-config-defaults.toml _output/incidents-config.d/
PROM=$(oc get route -n openshift-monitoring thanos-querier -o jsonpath='{.spec.host}')
AM=$(oc get route -n openshift-monitoring alertmanager-main -o jsonpath='{.spec.host}')
cat > _output/incidents-config.d/incidents.toml <<EOF
[toolset_configs."observability/incidents"]
auth_mode = "kubeconfig"
prometheus_url = "https://$PROM"
alertmanager_url = "https://$AM"
EOF
```

Do not reuse `dev/config/mcp-configs` as `MCP_CONFIG_DIR`: its `obs.toml`
sets `observability/metrics` to plain-HTTP localhost URLs, and the incidents
toolset prefers the metrics configuration — both backends must be HTTPS.

### 2. Kubeconfig with a trusted CA — `_output/eval-kubeconfig`

The toolset rejects `insecure` and verifies backend TLS. On OSD clusters a
kubeconfig from `oc login` uses `insecure-skip-tls-verify` without a CA,
which the observability transport ignores. Build a kubeconfig that carries
the CA chain instead:

```bash
B=$(mktemp)
# Route chain (leaf + self-signed ingress CA):
echo | openssl s_client -connect "$PROM:443" -showcerts 2>/dev/null \
  | sed -n '/BEGIN CERT/,/END CERT/p' >> "$B"
# API chain (leaf + intermediate) and cluster root CA:
API=$(oc whoami --show-server | sed 's|https://||; s|:.*||')
echo | openssl s_client -connect "$API:6443" -showcerts 2>/dev/null \
  | sed -n '/BEGIN CERT/,/END CERT/p' >> "$B"
oc get cm kube-root-ca.crt -n default -o jsonpath='{.data.kube-root-ca\.crt}' >> "$B"

CTX=$(oc config current-context)
CL=$(oc config view --raw -o jsonpath="{.contexts[?(@.name==\"$CTX\")].context.cluster}")
SRV=$(oc config view --raw -o jsonpath="{.clusters[?(@.name==\"$CL\")].cluster.server}")
USR=$(oc config view --raw -o jsonpath="{.contexts[?(@.name==\"$CTX\")].context.user}")
TOK=$(oc config view --raw -o jsonpath="{.users[?(@.name==\"$USR\")].user.token}")
cat > _output/eval-kubeconfig <<EOF
apiVersion: v1
kind: Config
clusters:
- name: eval-cluster
  cluster:
    server: $SRV
    certificate-authority-data: $(base64 -w0 "$B")
contexts:
- name: eval
  context:
    cluster: eval-cluster
    user: eval-user
current-context: eval
users:
- name: eval-user
  user:
    token: $TOK
EOF
chmod 600 _output/eval-kubeconfig
rm -f "$B"
```

The CA bundle serves both the observability transport (route certs) and the
server's Kubernetes client (API certs — client-go replaces system roots when
CA data is set, so the API chain and cluster root must be included). The
token is a copy of the current session token and expires with it.

### 3. Run

```bash
make run-server TOOLSETS='core,config,observability/incidents' \
  MCP_CONFIG_DIR=_output/incidents-config.d \
  MCP_EVAL_KUBECONFIG=_output/eval-kubeconfig
make run-evals SUITE=incidents
make stop-server
```

`run-server` generates `_output/eval-server.toml` and `_output/eval-config.d/`
from `MCP_CONFIG_DIR` — edit the source directory, never the generated copy.
`run-evals` installs mcpchecker and jq under `_output/tools/bin/`. The
`monitoring` UIPlugin with `clusterHealthAnalyzer.enabled: true` must exist
**before** the server starts; the toolset gate is evaluated at startup.
